# Host programs reach the Mac through a socket of their own server

On the Mac, an Agent's `muxify browser` command reaches the app through a Unix socket that the app names in `@muxify_browser_socket` (ADR 0057). On a Host, the app is on another machine, so today only `browser open` works there, through `@muxify_open` and the next poll. `muxify session open`, `window open` and `topic open` run macOS `open` and fail on Linux. We decide that each server on a Host (one per App Window's channel, [ADR 0086](0086-the-host-clis-server-lives-on-a-channel-of-the-attachments-ssh-master.md)) listens on a Unix socket of its own. It passes each line a program sends there to its Mac as a server-to-Mac `request` on the channel, and it sends the Mac's reply back on the socket. Host programs need only the socket. They never see the protocol, and the local and the remote paths behave the same.

- **The socket.** `<tmux socket_path>.muxify-browser.<server pid>`, in tmux's 0700 socket directory, the protection ADR 0057 relies on. The server unlinks it when it exits. A server that starts removes any `.muxify-browser.*` socket in that directory that refuses a connection, because a killed server leaves one behind. The socket protocol is ADR 0057's: one JSON request line and one reply line per connection.
- **Browser commands.** All of them work unchanged: `tabs`, `open`, `snapshot`, `click`, `fill`, `press`, `wait`, `eval`, `screenshot` and `close`. The `BrowserAgentRequest` travels inside a `browser` request. The Mac serves it with the Browsers of the App Window whose channel carried it. A `screenshot` comes back as base64 chunks of at most 64 KiB, and the CLI writes the PNG on the Host. As ADR 0057 says, no command activates the app or moves the responder.
- **Which server the CLI finds.** `@muxify_browser_socket` is one server-wide option, so it names one server: the server of the App Window that consumes `@muxify_open`, which is the App Window you used last on that Host, from any Mac. This is the local rule. When another App Window becomes the consumer, the Mac tells that window's server, which writes its own socket into the option. A server that exits clears the option only if it still names that server's socket. While the option is empty, any live server whose App Window consumes `@muxify_open` takes it.
- **View verbs.** On a Host, `muxify session open`, `window open` and `topic open` send a `select` request (`SelectRequest`) through the same socket instead of running `open`. The Mac shows the target in that App Window and brings Muxify to the front, as `open muxify://select` does locally. The CLI knows that it runs on a Host when `@muxify_browser_socket` names a Host Server's socket, by its `.muxify-browser.<pid>` name. A Browser command still sends the bare `BrowserAgentRequest` line, and a view verb sends `{"select": …}`, so the Mac app's own socket never sees a line it does not know.
- **Askpass.** When the server runs `git fetch`, `push` or `pull`, it sets `GIT_ASKPASS` and `SSH_ASKPASS` to the Host CLI's askpass helper, and passes the helper its own socket path in an environment variable. The helper connects to that socket. The tmux option is never used here, because it may name another server. The server sends `ask { prompt, secret }` to its Mac and hands the answer to git. When the server is gone, or the request ends as `cancelled` or `unavailable`, the helper fails at once, so git stops instead of hanging.
- **`muxify browser available`** still answers `local`, `remote` or `no` from the `@muxify_client_*` markers ([ADR 0056](0056-programs-find-muxify-by-the-server-it-shows.md)). Under `remote`, Browser commands now work, but the Mac's Browser cannot load the Host's `localhost`. In the Sessions-only fallback, Browser commands fail with "cannot reach Muxify", and `browser open` without `--json` still falls back to `@muxify_open`.
- **Only these three go from the Host to the Mac as requests:** Browser commands, view verbs and askpass. They ship with protocol 1, so they belong to its base and need no capability. The server pushes everything else as events: `@muxify_open` written by other programs, Agent Status, and Topic changes that other processes write to `muxify.db`.
- **The Local Environment does not change.** It keeps its socket at `<socket_path>.muxify-browser` and its "first store" routing, and its view verbs still go through macOS `open`.

## Considered Options

- **Forward a Host socket to the Mac's local socket with `ssh -O forward -R`**, which ADR 0057 proposed for later. Rejected:
  - sshd's `AllowStreamLocalForwarding` may be off.
  - `StreamLocalBindUnlink` defaults to `no`, so a leftover socket makes the next bind fail.
  - It is a second path beside the protocol.
  - The Mac's `BrowserAgentService` would then have to serve remote stores without knowing which App Window the request came from.
- **Send each Browser command to the App Window that now shows the caller's Session**, rather than to the one used last. Not now. It would change the local rule as well, and it leaves open where a `--tab` command goes when the App Windows switch Sessions. Local and remote keep one rule.
- **One shared socket owned by a daemon.** Rejected by the lifecycle decision ([ADR 0086](0086-the-host-clis-server-lives-on-a-channel-of-the-attachments-ssh-master.md)): no Muxify process outlives its channel.

## Consequences

- [ADR 0057](0057-an-agent-drives-its-windows-browser-through-the-muxify-cli.md)'s Consequence "A Remote Environment has no socket yet. Later, the app can forward the socket with `ssh -O forward -R`" is superseded.
- With two App Windows, or two Macs, on one Host, Browser commands and view verbs reach only the App Window you used last. A Tab that an Agent opened earlier stays in the App Window that opened it, as it does locally.
- The docs for `muxify browser available` and the `muxify` skill say what `remote` now means for Browser commands.
