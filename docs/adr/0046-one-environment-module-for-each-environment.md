# One Environment module for each Environment

Each Environment gets one Core module that is the only way to see and change it. App Windows, the CLI and later hosts are readers of the module. Today each App Window's `WorkspaceStore` reads tmux, keeps the Unread rule, wakes Snoozed Topics, ends Zen and remembers Topic Sessions. So two App Windows on Local read the same server twice and both write Unread and Topic memory. The module keeps one promise: the next state a reader sees includes every change it sent.

- **Every write goes through the module.** Callers send an `EnvironmentRequest`, and `EnvironmentService` becomes internal. The raw `select-pane`, `split-window`, `resize-pane`, `new-window` and `switch-client` calls in the app become requests too. Otherwise the promise is false for those changes.
- **One revision replaces the ordering flags.** Each write and each state has a revision: the id of the module and a number. The Router waits for the revision of its switch, not for a read number. A new module id, such as after a restart of `watch`, tells a reader to ask for a full state.
- **Every Perform gives a revision, a failed one too.** A request can fail after a part of it is done, for example after the records are saved, so a failure can also be a change. The state has a connection field that names a typed failure: no server, timeout or connection lost.
- **Viewing facts and visits come from each reader and are used only for Unread.** Each reader names its tmux Client, and sends what it shows, if the user can see it, and a visit when its navigation ends. The phone app sends them over the same protocol as the Mac app. A Pane is viewed if one reader views it. When a reader's stream closes, its Clients view nothing. A tmux Client that no reader names counts for nothing, as today. The module does not choose what a reader shows. Selection stays with each reader's tmux Client.
- **A visit is a request to the module.** The module sets the Agents and the Topic of the visited place Read, when Manual Read is off. Today the App Window writes the Topic records past the Service on a visit (`readTopicsOnVisit`), and only on Local.
- **The module runs on the machine that has the tmux server, and the app reaches it with one protocol for Local and Remote.** The protocol is JSON lines on the stdin and stdout of `muxify environment watch`. For Local, the app starts `muxify environment watch` as a child process. For a Remote, it starts `ssh -S <master socket> host muxify environment watch`. The client code in the app is the same for both, so daily use of Local also tests the Remote path. Inside the `watch` process the module is an actor in Core. Each App Window keeps a main-thread `@Observable` mirror that the client fills from the stream.
- **Who starts the module, and how long it lives.** The app starts the Local `watch` at launch and stops it when the app quits, so the clock rules and Unread work with no App Window open. The child exits at the end of its stdin, so an app crash also stops it. When the child crashes, the app starts a new one and asks for a full state. Two app processes, such as a Debug and a release build, each start a child, and the rules lock gives the rules to one of them. The app starts a Remote `watch` when the terminal's SSH master is ready, and it stops when that connection closes. The CLI makes its own module for one command, with Read now, queries and Perform only, because it must work when Muxify is not running. So the promise holds for each `watch` stream. Between processes, the file locks and the next read still apply.
- **The stream sends a full state once, then only changes.** Each line has a revision. A change line has the new values, not only names. A reader that finds a gap in the revisions, or connects again, asks for a full state. The client mirror builds a full state for each revision, so SwiftUI and the Router read full states, and the Unread rule and later readers use the list of changes.
- **The records watch stays a stamp poll**, one for each Environment. The module reloads at once after its own writes, so the poll finds only outside writes such as the CLI's. File events were rejected because a write of several records replaces the whole folder, and a watch on that folder loses it.
- **The interface is the wire.** The state, its list of changes, the revision and the viewing facts are `Codable`, like `EnvironmentRequest`, with no AppKit types and no callbacks. The app, the CLI and the phone app use the same types.
- **One module for each tmux server runs the rules.** It holds a rules lock, a file lock on the machine that has the tmux server. The module always runs on that machine, so every module of one server sees the same lock. Other modules, such as one CLI command, only read and perform, so the rules never have two writers. When nobody holds the lock, no rules run. The next module that takes it catches up: it upgrades records that an older Muxify wrote, and it finds Agent updates through the saved Agent Status.
- **The rules use the Config of the connecting client.** The client that starts a `watch` sends its rule settings, such as Manual Read, in its first line. A copied binary on a remote then follows the user's Mac Config, not an empty Config on the remote. A module that gets no settings, such as one CLI command, uses the Config file on its machine. The state shows the settings in force. When a Remote has more than one reader, a later decision says whose settings win.
- **The Unread rule keeps the last Status it saw in tmux,** as the pane option `@muxify_agent_seen_status`, not only in memory. It is written in the same tmux command list as the Unread change, and it goes away with its Pane. Today an Agent that finishes while no module runs never becomes Unread, because the rule has nothing to compare with after a start. With the Status in tmux, the next module that takes the rules lock finds the change.
- **No daemon.** The Local `watch` is a child of the app and stops with it. A Remote `watch` stops with its SSH connection. Muxify adds no process that runs on its own.
- **The app copies its own `muxify` to a remote.** It uses the universal binary in its bundle, so both ends have the same version. The copy goes to `~/.local/share/muxify/bin/<version>/muxify`. The app checks for that path in the first SSH call, copies only when it is missing, and keeps the last two versions. A Remote Environment's Topic records stay on the remote machine, and the remote `watch` reads them there, so every reader of that tmux server sees the same Topics.
- **A remote that cannot run `muxify` uses a fallback until a build for it exists.** The packages are `platforms: [.macOS(.v14)]`, so a Linux remote cannot run the copied binary. For such a remote, the app runs the same module in its own process with an SSH transport, behind the same protocol. This fallback has no Topics, as [ADR 0006](0006-remote-environments-use-owned-ssh-connections.md) describes, and its rules lock is on the Mac, so two Macs on one such remote can both run the rules.

## Considered Options

- **The phone reports its viewing facts through tmux**, with `list-clients` and a server option, `@muxify_hidden_clients`, for a phone app in the background. Rejected: the phone talks the same protocol as the Mac app, so it sends its facts directly, and a closed stream already means "not viewing".

- **The Local module in the app's process, and `watch` only for remotes.** Rejected: the app then has two clients, and daily use of Local does not test the Remote path. A child process also keeps a module crash out of the app.
- **A remote without `muxify` keeps today's SSH loop, with no copied binary.** Rejected: Topics and the rules then work only where the user installed `muxify` by hand, at a version that can differ from the app's.
- **Hide tmux fully**, with our own model and Pane streams in place of a tmux Client. Rejected for now: Muxify is a front end for tmux, and no second backend is planned. After this change tmux is behind the module, so this stays possible. Pane streams for a client that draws its own Panes go beside the module, not inside it.
- **Grouped Sessions, one for each Client**, so that two screens on one Session do not share the current Window. Rejected for now. Two Clients on one Session keep following each other, as tmux does today.

## Consequences

- A Local Environment's module is shared by all its App Windows. This changes [ADR 0007](0007-app-windows-have-independent-environments.md).
- A Remote Environment's module has one reader, because [ADR 0006](0006-remote-environments-use-owned-ssh-connections.md) ties the SSH connection to the terminal. More readers need a connection owner that is not the terminal.
- Each JSON line costs an encode and a decode. A Local prototype found no CPU cost from the protocol: at the same freshness, one reader of `watch` used the same CPU as today's loop. The gain comes from one read shared by all readers.
- The module must not make a Status change slower to show than today, in any Session. A tmux subscription checks only the attached Session, but an `S:` loop in its format covers every Session. With that push, a 5 s fallback read keeps Status as fast as today and uses less CPU.
