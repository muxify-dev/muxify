# The Mac app and the Host server speak newline JSON, and nothing is replayed

The Mac app talks to the Host CLI's server mode over one SSH channel. We decide that each message is one line of JSON, and that the protocol has no ack or replay layer. The payloads are the existing `EnvironmentRequest` and `EnvironmentResponse` Codable types, whose JSON form is already a contract pinned by tests. Round trips decide the speed of a remote App Window, not the codec. A request on an open channel costs one round trip, about 100 ms on a slow link, and decoding a whole snapshot as JSON costs 0.3 ms on the Mac and 0.55 ms on the Host. JSON needs no schema file, no generated code and no mapping layer in Swift. The phone already reads the Host CLI's JSON with its own UTF-8 decoder, since Hermes has no `TextDecoder`. A person can read the stream and drive the server by hand.

- **Frame**: one JSON line ending in `\n`, at most 16 MiB. A longer line is a protocol error and closes the channel. `JSONEncoder` escapes newlines inside strings, so a line is always exactly one message.
- **Preamble**: the server's first line is `MUXIFY-PROTOCOL`. The Mac discards anything before it, up to 64 KiB, because a login shell can print to stdout before the server starts (fish's `config.fish` always runs). If the magic line does not arrive, the Mac fails, says how many bytes the shell printed, and shows the first line of them.
- **Envelope**: `id` plus `kind`, which is one of `hello`, `request`, `item`, `end` or `cancel`, and the payload under the key that `kind` names: `{"id":1,"kind":"request","request":{"ping":{}}}`. Either side sends requests. Each side numbers its own from 1 and never reuses an id on a channel. `item` and `end` carry the id of the request they answer, `cancel` the id of the request it cancels, and `hello` the id 0. Keys are snake_case, as in `EnvironmentRequest`.
- **Every request ends exactly once**: zero or more `item`s, then one `end`. `end` holds either `ok`, with the request's answer or `{}`, or `error { code, message }`, and the codes are `unsupported`, `invalid`, `cancelled`, `unavailable` and `failed`. A domain failure is `failed`, with MuxifyCore's message. A streamed response is base64 chunks of at most 64 KiB, sent as `item`s. A subscription is a request whose `item`s are events; its `end` comes only from a cancel, an error or the end of the channel.
- **Cancel**: `cancel { id }` works on any open request. The receiver tells the handler to stop and answers `cancelled`. A mutation that has already started finishes, and its `end` reports what actually happened. A request that the client made before the handshake finished is cancelled where it waits, and never written.
- **Backpressure**: there is no credit scheme. Each side has the SSH channel's flow control and one bounded writer queue, with chunks interleaved among other frames. Events push state, not deltas, so a newer event replaces an unsent one with the same key. A subscriber that cannot keep up is ended with `unavailable` and subscribes again.
- **No ack and no replay**: when the channel ends, every open request fails at once with `unavailable`. A mutation's outcome is then unknown, and it is never sent again (ADR 0006). After a reconnect, each subscription is opened again, and its first `item` is the full current state.
- **Hello**: the server sends its `hello` right after the magic line, and the Mac answers with its own. Each carries `protocol` (an integer), `build` (the `muxify --version` line) and `capabilities` (strings); the server's also carries `min_protocol` (ADR 0086). The Mac waits up to 10 s for the server's `hello`, and neither side sends a request before it has the other's. A request that comes before it is a protocol error. `ping` is an ordinary request.
- **stderr** is plain-text log lines, never parsed. The Mac keeps the last 50 and logs them, quoting the last one, only when the channel fails.
- **No compression** in the protocol. SSH's `Compression` option is there for a user who wants it, and a large payload that needs compression later gets a compressed field of its own.

- **In code**: the types, the codec, the client half (`ProtocolClient`) and the server half (`ProtocolServer`, and `HostServer` for `muxify server`'s requests) live in MuxifyCore's `Protocol` folder, so the Host CLI, the Mac app and tests share them. The client half takes a pair of file handles: an SSH channel's, or a test's pipes.

## Considered Options

- **Protobuf, framed by a length prefix** (Zed's choice). It is 6–15× faster to code, a third of JSON's size, and an older peer keeps unknown fields. Rejected: the speed saves under half a millisecond against a round trip. It costs a `.proto` file, about 1,000 generated lines per 15 messages, a mapping in both directions, a code generation step in two repositories, a `TextDecoder` polyfill and `bigint` int64 on the phone, and about 1.5 MB on the Host CLI.
- **MessagePack through Codable.** It keeps the existing types for about 0.3 MB. Rejected: it is still binary, nobody can read it, and its library's last commit was in 2024.
- **Ack and replay across reconnects** (Zed, VS Code, distant). Rejected: replaying a mutation whose outcome is uncertain is what ADR 0006 forbids, and Zed's open bug of requests that hang forever after a reconnect lives in that layer. The server keeps no state across a drop to replay into.

## Consequences

- JSON is about three times protobuf's size: about 20 KB for a whole snapshot, about 160 ms on a 1 Mbit/s cellular link. Events that cover one Topic or one Session, not the whole snapshot, keep this small.
- An unknown command case does not decode. The server answers `unsupported`, so a newer Mac can still talk to an older server for every request the older one knows.
- Raw bytes, such as an upload or a large diff, travel as base64, which is 33% bigger.
