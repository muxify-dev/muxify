# A Config can name Overrides that merge on top of it

The Config's top-level `override` key names one Config Override path or a list of them, such as `override: ~/.config/muxify/config.override.yaml`. The user keeps one Config under git and adds per-machine settings in a file that only that machine has. Muxify merges the YAML before it reads it, as if one file had been written. A mapping merges key by key. A list or a single value in a Config Override replaces the Config's whole: an Override's `sessions.paths` replaces the shared list, and `keybindings.toggle_sidebar: []` clears that action. Config Overrides apply in list order, and a later one wins. A key the Config already has keeps its place in the merged result even when an Override changes its value. A key that only an Override adds comes after the Config's keys, in that Override's order, so "the first action in the file" (ADR-0005) still has one meaning. An Override cannot remove a key to bring back Muxify's default, and `null` keeps its current meaning. The Override writes the default value instead.

A Config Override that does not exist is skipped with no problem, because a machine without its own file is the normal case. Only the Config itself may name Config Overrides. An `override` key inside a Config Override is a problem and is ignored. An Override path is `~/`-based, or relative to the Config's directory. Each value keeps the file it was written in. A relative path in it resolves against that file's directory, and a problem with it shows that file's path and line. The banner lists problems by file (the Config, then each Override in list order) and then by line. A YAML syntax error in any Config Override is treated like one in the Config: the last good merged Config stays, and the banner shows the error. Muxify watches the Config Overrides with the Config, missing ones included. A Remote Environment's Config can name its own Config Overrides, and Muxify reads them on that machine over the Environment's owned SSH connection whenever it reads that Config.

This reverses ADR-0005's "Includes. Dropped for now", and it narrows ADR-0010's "one file per machine" to one Config per machine with its Config Overrides. Keybinding collisions are decided over the merged result, so they can span files. That is not the overlay ADR-0010 rejected: that overlay put one machine's Config over another's, and here every file belongs to the same machine.

## Considered Options

- **chezmoi templates for per-machine files**, as ADR-0005 suggested. Rejected: they need a template engine around a file that Muxify reloads live, and the user wants a plain file in git plus a plain local file.
- **Append lists, as Docker Compose does.** Rejected: an Override could then never remove a shared Session Path or keybinding without extra tags such as Compose's `!reset`.
- **A missing file is a problem unless its path starts with `?`, as in Ghostty's `config-file`.** Rejected: the whole point is a file some machines lack, so every entry would need the `?`. The cost is that a typo in an Override path is silent too.
- **Nested Overrides.** Rejected: one level is enough for per-machine settings, and with no recursion there are no cycles to detect.
- **Ignore `override` in a Remote Environment's Config.** Rejected: a remote App Window would quietly lose that machine's settings, and ADR-0010 says it behaves as if Muxify ran there.
